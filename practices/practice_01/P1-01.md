# P1-01: Замечания по TRAINING_PR.diff

Ниже перечислены проблемы и риски в предложенном diff. Структура: по файлам, с детализацией по типам ошибок (совместимость, корректность, архитектура, безопасность, DX/документация).

## app/review_service.py

1. Совместимость типов (Python version):
   - Используется `dict[str, str]` в аннотациях (PEP 585). Это требует Python ≥ 3.9. Без `from __future__ import annotations` на Python 3.8 такой код не запустится. Контекст версии в репозитории не указан.

2. Совместимость `Protocol`:
   - Применяется `typing.Protocol`. Для Python 3.7 нужен `typing_extensions`. Без явного указания целевой версии — риск несовместимости.

3. Метод `ReviewService.review` — надежность и безопасность:
   - Нет валидации входа `diff` (пустая строка, чрезмерный размер, тип). Любой ввод отправляется в LLM.
   - Конкатенация prompt без изоляции содержимого diff. Подвержено prompt injection: текст diff может менять поведение LLM. Нет ограждающих маркеров/инструкций (например, тройных кавычек, явных ролей/границ).
   - Возвращается «сырое» содержимое LLM: `{"comment": answer}`. Ответ неструктурирован (свободный текст), что делает клиентов нестабильными и осложняет автоматическую проверку/тестирование.
   - Нет обработки ошибок/таймаутов LLM. Исключения из `generate` приведут к 500 на уровне API.

4. Качество и локализация:
   - Нет докстринга/описания поведения. Это затрудняет сопровождение.
   - Жестко задан англоязычный prompt при том, что артефакты курса на русском. Несоответствие локали/ожиданий.

5. Нестабильный контракт:
   - Метод возвращает только один ключ `comment`. Для задачи «найти проблемы» разумнее структурированный список с атрибутами (severity, файл, строка, сообщение). Текущая форма ограничивает полезность downstream-логики.

## app/api.py

1. Валидация входа и схема:
   - Сигнатура `create_review(payload: dict)` не использует Pydantic-модель. В FastAPI это ведет к отсутствию строгой схемы, слабой документации и валидации.
   - Доступ по ключу `payload["diff"]` без проверки приводит к `KeyError` и 500 при отсутствии поля. Корректно — валидация с 422 и явное сообщение об ошибке.

2. Совместимость типов (Python version):
   - Аннотация `-> dict[str, str]` требует Python ≥ 3.9, см. замечание выше.

3. Инъекция зависимостей и тестируемость:
   - Импортируется глобальный `review_service` из `app.dependencies`. Нет использования механизма `Depends`. Это усложняет подмену зависимостей в тестах и привязывает endpoint к глобальному состоянию.

4. Обработка ошибок и статусы:
   - Нет перехвата ошибок LLM/сервиса и маппинга на `HTTPException` с осмысленными кодами/сообщениями. Любая ошибка приведет к 500 без объяснения.

5. Документация/OpenAPI:
   - Нет `response_model`, нет `summary/description/tags`. OpenAPI-схема для тела запроса будет «свободной» (произвольные ключи), а обязательность `diff` не отражена.

6. Производительность:
   - Endpoint синхронный. Если `llm.generate` выполняет сетевой/IO-запрос, это блокирует воркер-пул. Требуется оценка: либо сделать асинхронный интерфейс, либо явно контролировать threadpool и таймауты.

7. Безопасность и эксплуатация:
   - Нет аутентификации/авторизации на `POST /api/reviews`. Любой клиент может инициировать дорогие LLM-запросы (риск злоупотребления и затрат).
   - Нет ограничений на размер тела запроса/поля `diff`, что может привести к DoS/перерасходу токенов.

8. Локализация и сообщения:
   - Сообщения/ошибки для клиента не определены; при ошибках будут возвращаться дефолтные ответы сервера (англ.).

## Прочие наблюдения

- Изменение сигнатуры метода в `LLM` на многострочную форму с `...` — косметика, но нарушает единообразие стиля без понятной выгоды.
- Нет тестов/примеров контрактов для нового endpoint и сервиса (по файлам практики это ожидается, но в diff их нет).

## Итог

Основные проблемы — отсутствие валидации и схем (Pydantic), отсутствие обработки ошибок, небезопасный и неструктурированный prompt/ответ, потенциальная несовместимость по версии Python из-за использования `dict[str, str]`, слабая интеграция с DI FastAPI и отсутствие механизмов безопасности и ограничений. Эти пункты влияют на надежность, тестопригодность, безопасность и эксплуатационные затраты.
