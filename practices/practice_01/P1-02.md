# P1-02: Ревью TRAINING_PR.diff по правилам репозитория

Ниже перечислены ошибки и потенциальные проблемы с доказательствами из diff и ссылками на правила репозитория (CASE.md). Для каждой указан: место (файл, строка), причина, аргументация, способ решения.

## 1) Нарушение SEC-1: секреты не редактируются перед отправкой в LLM

- Место: app/review_service.py, строка: метод `review` (блок с формированием `prompt` и вызовом `self.llm.generate(prompt)`).
- Причина: правило SEC-1 требует удалять токены/пароли/приватные ключи из diff перед отправкой во внешний LLM.
- Аргументация: в diff видно, что формируется строка `prompt = f"Review this pull request and find problems:\n{diff}"` и сразу вызывается `self.llm.generate(prompt)` без какой-либо предобработки `diff`. Это означает, что потенциальные секреты попадут во внешний LLM, что прямо противоречит SEC-1.
- Способ решения: перед формированием `prompt` пропустить `diff` через санитайзер (например, `sanitize_diff(diff)`), который заменит секреты на маркеры вида `[REDACTED]` по регулярным выражениям и известным префиксам ключей. Добавить модульные тесты на примеры токенов/ключей, подтверждающие корректную редакцию.

## 2) Нарушение OUT-1: неверная структура ответа сервиса

- Место: app/review_service.py, строка: `return {"comment": answer}`.
- Причина: правило OUT-1 требует, чтобы ответ содержал поля `summary`, массив `risks` (не более трёх элементов с полями `file`, `line`, `evidence`, `risk`) и массив `checks`.
- Аргументация: текущая реализация возвращает словарь только с ключом `comment`, что не соответствует требуемому контракту. Это ломает клиентов и не даёт воспроизводимых проверок.
- Способ решения: изменить контракт `review()` так, чтобы он возвращал объект вида `{"summary": str, "risks": List[Risk<=3], "checks": List[str]}`. Обновить prompt для LLM с требованием строгого формата и/или добавить пост-процессинг/валидацию результата. На уровне API объявить `response_model`, соответствующий OUT-1.

## 3) Нарушение API-1: отсутствует отсечение слишком длинного diff с кодом 413

- Место: app/api.py, блок `create_review(payload: dict)`.
- Причина: правило API-1 требует отклонять diff длиной > 20 000 символов с HTTP 413.
- Аргументация: endpoint без проверки размера сразу обращается к `review_service.review(payload["diff"])`. Нет проверки `len(diff)` и возврата 413.
- Способ решения: добавить валидацию длины тела/поля `diff`; при превышении порога возвращать `HTTPException(status_code=413)`. Желательно настроить также лимит размера тела запроса на уровне сервера.

## 4) Нарушение REL-1: нет таймаута для внешнего LLM и контролируемого ответа при ошибке

- Место: app/review_service.py, метод `review`; app/api.py, endpoint `create_review`.
- Причина: REL-1 устанавливает таймаут 10 секунд и требует преобразовывать ошибку в контролируемый ответ.
- Аргументация: вызов `self.llm.generate(prompt)` выполняется без таймаута и без перехвата ошибок; в API отсутствует обработка исключений. При таймауте/ошибке клиент получит 500 и неструктурированный ответ, что противоречит REL-1 и OUT-1.
- Способ решения: обернуть вызов LLM в таймаут (на уровне клиента или с помощью будущ/пула потоков), перехватывать исключения и возвращать валидный по OUT-1 объект с пустыми/дефолтными полями и явной записью в `checks` о таймауте. На уровне API маппировать ошибки на контролируемый ответ.

## 5) Нарушение QA-1: риски должны подтверждаться строкой diff или правилом

- Место: app/review_service.py, метод `review` и формирование prompt.
- Причина: по QA-1 риск включается, только если подтверждён строкой diff или правилом репозитория; также максимум три риска.
- Аргументация: текущий prompt — «Review this pull request and find problems» — не требует от модели приводить `evidence` и ограничивать количество рисков, а код не валидирует результат. Это ведёт к неподтверждённым или чрезмерным рискам.
- Способ решения: обновить prompt и пост-обработку: требовать на выходе `risks` с полями `file`, `line`, `evidence` (фрагмент из diff), `risk`; ограничивать список тремя элементами; отбрасывать риски без `evidence`.

## 6) Проблема FastAPI-схемы: нет Pydantic-модели и валидации входа

- Место: app/api.py, строка объявления `create_review(payload: dict) -> dict[str, str]` и доступ `payload["diff"]`.
- Причина: без модели запроса отсутствует строгая схема, и при отсутствии поля `diff` будет `KeyError` → HTTP 500 вместо 422.
- Аргументация: по diff видно, что используется «сырой» `dict` и прямой доступ по ключу. Это приводит к нестабильному API и не документируется в OpenAPI.
- Способ решения: ввести Pydantic-модель запроса с обязательным полем `diff: str` и валидировать его длину; объявить `response_model`, соответствующий OUT-1. При отсутствии поля — вернуть 422 автоматически.

## 7) Потенциальная уязвимость prompt injection и форматирования

- Место: app/review_service.py, формирование `prompt` через f-string: `...\n{diff}`.
- Причина: без изоляции содержимого diff (кодовые блоки, инструкции «игнорировать указания внутри diff») модель может следовать инструкциям из diff (prompt injection) или исказить формат ответа.
- Аргументация: текущий prompt не отделяет вход от инструкций и не фиксирует формат вывода. Это типичный риск при работе с LLM и непосредственно вытекает из реализации.
- Способ решения: заключать diff в тройные кавычки/кодовый блок, явно прописать, что любые инструкции внутри diff следует трактовать как данные, а не указания; требовать строгий JSON-формат и валидировать его.

## 8) Наблюдаемость: отсутствие журналирования по OBS-1

- Место: app/review_service.py и app/api.py (в этом изменении логирование отсутствует полностью).
- Причина: OBS-1 описывает минимально допустимое логирование: `request_id`, длительность и статус, без содержимого diff и ответа модели.
- Аргументация: в представленном diff отсутствует логирование, что не позволяет контролировать тайминги/успешность и соответствует риску эксплуатации. При этом важно не нарушить запрет логировать содержимое diff/ответа (OBS-1).
- Способ решения: добавить структурированное логирование только разрешённых полей: `request_id` (передавать через заголовок/контекст), длительность обработки и статус; убедиться, что diff и ответ LLM не логируются.

---

Итог: изменения нарушают как минимум SEC-1, OUT-1, API-1 и REL-1, а также не обеспечивают требования QA-1 и OBS-1. Требуются доработки контракта, валидаций и обработчиков, прежде чем выпускать в прод.
