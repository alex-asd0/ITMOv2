## Ответ со ссылками на источники

Извлечённые факты:

- SEC-1: перед отправкой во внешний LLM из diff удаляются токены/пароли/приватные ключи (CASE.md: 64). Под это есть unit-тест «Редакция секретов в diff» (tests_unit.md: 5).
- API-1: diff > 20 000 символов отклоняется с HTTP 413 (CASE.md: 65). Интеграционный тест подтверждает 413 без обращения к LLM (tests_integration.md: 5).
- REL-1: LLM-вызов с timeout 10 секунд; ошибка превращается в контролируемый ответ (CASE.md: 66). Интеграционный тест: таймаут/ошибка → контролируемый ответ по OUT-1 (tests_integration.md: 6); E2E негативный сценарий — без 500 (tests_e2e.md: 6).
- OUT-1: ответ содержит summary, risks (≤3, с file/line/evidence/risk), checks (CASE.md: 67). Unit-тест ограничивает risks<=3 и требует evidence (tests_unit.md: 6). E2E позитивный сценарий ожидает JSON по OUT-1 (tests_e2e.md: 5).
- QA-1: включать только подтверждённые риски; максимум три (CASE.md: 69). Проверка опирается на unit-тест OUT-1 (tests_unit.md: 6).
- OBS-1: логируются только request_id, длительность и статус; diff и ответ модели не логируются (CASE.md: 70). Используем как ограничение при проектировании.
- Примеры комментариев: хороший и плохой (CASE.md: 79–91) для ориентира качества.
- Зафиксированные нарушения и способы исправления для этих правил перечислены в P1-02 (пп. 1–5, 8).
