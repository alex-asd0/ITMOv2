# ADR: решение для первого рабочего сценария

- Статус: proposed
- Критерий перехода в accepted: пройдут проверки из tests_unit.md, tests_integration.md, tests_e2e.md, tests_load.md на соблюдение SEC-1, API-1, REL-1, OUT-1/QA-1 и OBS-1
- Дата: 2026-09-09
- Ответственные: команда разработки сервиса ревью

## Контекст

Сервис получает diff PR и пересылает его во внешний LLM. По CASE.md действуют правила SEC-1, API-1, REL-1, OUT-1, SCOPE-1, QA-1, OBS-1. Текущая версия нарушает несколько из них.
## Решение

- API-1: отклонять diff длиной > 20 000 символов кодом 413; на уровне API валидировать вход.
  Как проверим: см. tests_integration.md — сценарий «Превышение размера diff» (413) и tests_e2e.md — «Граничный: diff=ровно 20000»/«Позитивный».

- SEC-1: перед вызовом внешнего LLM редактировать секреты в diff (замена на [REDACTED]) и изолировать содержимое diff в промпте от инструкций пользователя.
  Как проверим: см. tests_unit.md — строка «SEC-1: Редакция секретов в diff».

- REL-1: оборачивать вызов внешнего LLM таймаутом 10 секунд; ошибки преобразовывать в контролируемый ответ без 500.
  Как проверим: см. tests_integration.md — «Таймаут/ошибка LLM → контролируемый ответ», tests_e2e.md — «Негативный: симулированная ошибка LLM», tests_load.md — 95-й перцентиль < 1s при 10 RPS.

- OUT-1 и QA-1: возвращать строго структурированный ответ: `summary`, массив `risks` (≤3 элемента с `file`, `line`, `evidence`, `risk`) и массив `checks`; отбрасывать риски без evidence.
  Как проверим: см. tests_unit.md — строка «OUT-1: ограничение risks<=3 и evidence»; tests_e2e.md — «Позитивный: 200; JSON по OUT-1».

- OBS-1: вести минимальное структурированное логирование только разрешённых полей (`request_id`, длительность, статус) без содержимого diff/ответа модели.
  Как проверим: см. tests_integration.md — запуск интеграционных сценариев; дополнительно вручную убедиться по логам, что содержимое не пишется (Unconfirmed автоматическими тестами).

Не расширять полномочия сервиса за пределы SCOPE-1: сервис только советует, код не меняет.
  Как проверим: см. CASE.md — правило SCOPE-1; поведение наблюдается в e2e-сценариях (не выполняются действия вне ответа).
## Рассмотренные альтернативы

| Альтернатива | Почему не выбрали сейчас |
|---|---|
| Передавать diff как есть | Нарушает SEC-1 и повышает риски утечки |
| Свободный текст вместо OUT-1 | Непригодно для автоматической проверки и нарушает OUT-1 |
| Отсутствие таймаута | Нарушает REL-1, ведёт к нестабильности |

## Последствия и главный риск

- Положительные последствия: соблюдение SEC-1/API-1/REL-1/OUT-1/QA-1 повышает безопасность и стабильность; формат ответа предсказуем для клиентов (OUT-1).
- Ограничения: дополнительные накладные расходы на санитайзинг/валидацию (SEC-1/OUT-1) и дисциплину логирования (OBS-1).
- Главный риск: ложная редакция секретов (скрытие полезного контекста) или пропуск секрета (SEC-1); при сбоях риск нарушения формата OUT-1.
- Как проверим риск: tests_unit.md (SEC-1: редактирование секретов) и tests_integration.md/tests_e2e.md (контролируемые ответы при ошибках, соответствие OUT-1).
